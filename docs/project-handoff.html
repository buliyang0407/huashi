项目概况

这个项目是什么

一个私有“画室”网页应用，用来管理 RunningHub AI 应用、提交生图任务、保存记录、整理画册、维护提示词库，并做提示词智能拆解和衍生。

主要用户习惯

移动端优先，但 PC 端也要好用。界面要干净、少按钮、像手机相册一样自然；复杂功能放在管理端或二级入口。

技术形态

后端没有 FastAPI/Flask，使用 Python 标准库 HTTP server；数据存在 SQLite 和本地文件夹；前端是 web/app.js 等原生文件。

数据保护红线

不要删除 NAS 数据。 这个项目的数据比代码更重要。部署、备份、Git 操作都必须遵守下面几条：

  • .env 不进 Git、不写真实密钥到文档。
  • data/ 不进 Git、不用本地空目录覆盖 NAS 的 data/。
  • pose/ 很大，只作为 NAS 共享资源和 Docker 只读挂载，不打包、不复制到仓库。
  • 部署前在 NAS 上调用“写入备份”接口；如果需要清理，先问用户。
  • 压缩代码包时显式排除 data、pose、.env、.git、.playwright-cli。

当前功能地图

AI 应用

首页展示已配置 RunningHub 应用。管理端可新增、编辑、删除应用，支持封面图、默认图标、输入字段、下拉选项、数字项、提示词输入框识别。

生成记录

提交任务后保存完整设定、提示词、上传文件名和输出图。记录支持重试、删除、保存提示词、复制提示词、输出图模糊和单张删除。

画册

原“作品”已改为“画册”。有文件夹入口，可新建文件夹、上传图片、移动图片、手动排序。生成结果默认进入“作品”文件夹，列表按最新在前。

POSE 画册

NAS 项目目录下的 pose/ 作为只读虚拟画册展示。按文件夹逐层浏览，分页懒加载，避免一次性扫入几千张图。

提示词库

保存常用提示词，每条提示词可配图、标签、搜索、复制、衍生提示词。应用里的提示词输入框可从提示词库选择。

智能拆解

提示词旁有“智能拆解”。先结构化分析核心画面、可修改点和不建议改的点，再根据用户要求生成一个高质量衍生版本，并可继续细改。

画册与作品库注意事项

  • AI 应用选择“作品库”时必须先进入画册文件夹列表，不能直接沿用上一次打开的 POSE 子目录。
  • 普通画册图片记录在 SQLite，文件位于 data/albums/uploads 或任务缓存目录。
  • POSE 是虚拟只读来源，不导入数据库，不允许删除和移动真实文件。
  • 生成图如果在画册里删除，应该隐藏/删除该单张输出；不要误删整个任务，除非用户点的是记录删除。
  • 手机端画册查看器要尽量全屏，少按钮，保留返回、删除、模糊等必要动作。

提示词智能拆解设计

这个功能不是外部 OpenWebUI，也不是复杂 Agent 平台，而是内置在画室里的“结构化拆解 + 单条衍生 + 多轮继续修改”。

  1. 分析：输入原提示词，返回类型、核心画面、核心不变点、可修改点、不建议修改点、中文引导。
  2. 生成：输入分析结果和用户修改要求，只生成一个候选，包含英文完整提示词、中文直译/理解、特点摘要。
  3. 继续改：选中某条衍生提示词后，基于这条继续按用户要求修改。
  4. 保存：衍生提示词挂在原提示词下面，形成上下文链路，不能简单拼接进同一个文本框。

代码结构

路径 职责
huashi/server.py HTTP 路由、静态文件、API 入参处理。
huashi/service.py 业务逻辑：任务、应用、画册、提示词、备份。
huashi/storage.py SQLite schema、数据读写、迁移。
huashi/runninghub.py RunningHub API 客户端、文件上传、任务创建和输出下载。
huashi/runninghub_inspector.py RunningHub 应用页面解析和字段识别。
huashi/prompt_ai.py 提示词改写/翻译模型调用，支持 AIHubMix 和 Ollama。
huashi/prompt_agent.py 智能拆解、生成、继续修改的模型封装和 JSON 容错。
web/app.js 主应用前端：首页、生成、记录、画册、提示词。
web/admin.js 管理端前端：应用配置、备份、字段检查。
tests/ 后端单元测试。当前主要覆盖 storage/service/inspector/prompt。

本地验证

python3 -m unittest discover -s tests -v
node --check web/app.js
node --check web/admin.js
python3 -m py_compile huashi/*.py

部署前备份 NAS 数据

ssh buliyang@192.168.3.71 'curl -s -X POST http://127.0.0.1:8787/api/admin/backup/write'

安全打包代码

tar \
  --exclude='.git' \
  --exclude='.env' \
  --exclude='data' \
  --exclude='pose' \
  --exclude='.playwright-cli' \
  --exclude='*.tgz' \
  -czf /tmp/huashi-code.tgz .

NAS 上重建容器

ssh buliyang@192.168.3.71 'cd /volume1/docker/runninghub && docker compose up -d --build'

如果只改静态文件，仍建议重启容器或至少确认浏览器缓存版本。当前前端文件通过 web/index.html 中的资源版本号做缓存刷新。

GitHub 与提交规则

  • 远端仓库：https://github.com/buliyang0407/huashi.git。
  • 从 main 开发时优先新建 codex/... 分支，再 push 和开 PR。
  • 提交前检查 git status --short，确认没有 .env、data/、pose/、大压缩包、Playwright 缓存。
  • 如果用户明确要求直接上 main，再按用户要求操作；否则保留 PR 审核路径。

已知注意点

  • 单元测试目前会出现一些 sqlite 连接 ResourceWarning，但测试结果是通过的；后续可以单独整理连接关闭。
  • RunningHub 不同应用页面字段差异很大。新增应用时最好用管理端检查器辅助，再人工复核图片框、提示词框、下拉框和数字输入。
  • “高级洗图”等带 ZIP 输出或特殊审核逻辑的应用，历史上容易出错，新增或修改时要用真实小图跑一遍。
  • 画册里 POSE 文件量大，任何递归扫描、缩略图预生成、批量导入都要谨慎，先做分页或懒加载。
  • 提示词智能拆解依赖第三方模型质量。Grok/AIHubMix 当前作为主力，本地 Ollama 只是备用。
